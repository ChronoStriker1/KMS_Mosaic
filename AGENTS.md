# AGENTS.md (Project Guidance)

The role of this file is to describe common mistakes and confusion points that agents might encounter as they work in this project. If you ever encounter something in the project that surprises you please alert the developer working with you and indicate this is the case in the AgentMD file to help prevent future agents from having the same issue.

## Surprises / gotchas
- On TOWER, amdgpu can fail the boot-time EDID read on a connected monitor (`EDID err: 2, on connector: HDMI-A-1` in dmesg), so that port reports `disconnected` until something re-probes it. `--connector monitor:NAME` therefore waits instead of exiting: the compositor re-probes every 2 s (`drmModeGetConnector` forces a probe) and writes the selector to `KMS_MOSAIC_OUTPUT_WAIT_FILE` while it waits. The service passes `/var/run/kms_mosaic.waiting-output` there, pauses the frame watchdog while it exists, and treats it as a successful start (`startup-waiting-for-output`). Without that, the start routine's two attempts fail and it stops the supervisor for good.
- Overwriting `/boot/config/plugins/kms.mosaic.plg` before running `plugin install` makes Unraid see the same version and skip the install, because `/var/log/plugins/kms.mosaic.plg` links to that file. Installing from a temp copy with another file name registers a second plugin under that name. Stage the new manifest as `kms.mosaic.plg` in a temp folder and install from there.
- A media/config save can leave an in-process `execv()` reload alive at high CPU while producing no first frame, even though the same saved config starts normally through a clean service restart. Plugin-managed reloads therefore exit with code 75 for a fresh supervisor launch, and the service also requests periodic fresh frames so it can replace a live-but-unresponsive compositor.
- The compositor supervisor's fresh-frame watchdog and pane-child group tracker must run in a dedicated monitor process while the parent waits for `kms_mosaic.bin`. During the wrapper-to-binary exec transition, an inline loop could fall through into `wait`, disabling health checks while a wedged compositor stayed alive. The monitor uses `/proc/<pid>/stat` plus `kill -0`, and health checks begin immediately at launch.
- Even with `LOG_ENABLE="disable"`, the plugin supervisors retain bounded application tails in `/tmp/start_kms_mosaic.log` and `/tmp/kms_mosaic_web.log`, plus persistent lifecycle/exit-status events in `/boot/config/plugins/kms.mosaic/lifecycle.log`. Check those before reproducing a crash; verbose logging is not required for basic postmortem evidence.
- Treat TOWER deployment as a release gate for every program update: build both the Linux and Unraid artifacts, install the completed artifacts on TOWER, verify installed hashes, service health, physical output, advancing frames, WebRTC preview, and pane alignment, then commit and push only after those checks pass.
- Restarting `kms_mosaic` on the Unraid host is sensitive to stop/start ordering. Do not stop and start in parallel. `pkill -f` can also match the remote shell command line and race badly. Use an exact-name stop like `pkill -x kms_mosaic.bin`, wait briefly, then start the plugin service or wrapper.
- The active config file is watched at runtime. Layout/UI-only changes are applied in-process and keep the PID; pane/media/process changes self-reexec through the packaged wrapper, so do not assume every config save preserves the PID.
- The old Unraid userscript can override runtime behavior independently of the repo. On this host it had `KMS_MOSAIC_DISABLE_CONFIG_WATCH=1`, which silently disabled live config reload even though the binary supported it. If a runtime feature mysteriously stops working, check whether the host is still launching through the old userscript instead of the plugin.
- The retired `Start kms_mosaic` userscript on the Unraid host did not use `cec-client`; its monitor setup was raw DDC/CI writes from inline Python to `/dev/i2c-3` at slave address `0x37`. If you are trying to recover or replace the old monitor-control behavior, start from DDC/CI bus discovery and VCP capabilities, not from CEC assumptions.
- KMS Mosaic must not send DDC/CI commands. The separate `monitor.control` plugin owns monitor settings and restores them when they drift. The old startup write forced color preset 7500K, brightness 100 and contrast 100 on every compositor start, then saved them to the monitor.
- Even with the correct sequential flow, a fast restart can still hit `drmModeAtomicCommit (modeset): Permission denied` on the Unraid host. If that happens, wait a few seconds and start it again.
- The plugin service stop path can hit wedged `kms_mosaic.bin` PIDs that ignore a normal `SIGTERM`. If restart appears to do nothing, check whether the old PID survived and use an exact-PID `SIGKILL` fallback before starting again.
- After replacing the web wrapper in place, `kms_mosaic-service start` can briefly write a PID file for a launch that has already vanished while still reporting `web_running=true`. Verify the command line and HTTP port after a web-only update; if they are absent, clear the stale PID file and launch `/usr/local/bin/kms_mosaic_web` detached once.
- A restart can also miss the new launch if the old exact-name `kms_mosaic.bin` PID is still visible briefly after `SIGKILL`; `start_kms` sees it and returns, then the old PID exits and the service is left down. The service script should wait for exact-name PIDs to clear before starting again.
- A one-shot `pgrep -P "$kms_pid"` child snapshot is not sufficient for plugin shutdown cleanup. Pane helpers can reparent while `kms_mosaic.bin` is still exiting, so `scripts/kms_mosaic-service` needs to refresh and union child process groups during the stop wait loop before killing those groups.
- The containerized packaging path is the most reliable validation route on non-Linux hosts. If you need a Linux build locally, prefer `scripts/macos_build_pkg.sh` over the host `make` path.
- Release packages are not committed. `dist/` is gitignored and untracked since 2026-11-17, when the 27 tracked packages had reached 854 MB and GitHub warned about the 71 MB `.txz`. Each version's `.txz` and `.tgz` are assets on the GitHub release tagged with the version, and the manifest downloads them from `https://github.com/ChronoStriker1/KMS_Mosaic/releases/download/<VERSION>/`. Git LFS would not work, because Unraid fetches plain URLs and `raw.githubusercontent.com` serves LFS pointer files. Release flow: bump `VERSION`, the plugin `VERSION` file and the manifest (with a `###<VERSION>` CHANGES entry), build, deploy and verify on TOWER, commit, run `scripts/publish_release.sh` (pushes the tag, creates the release, and checks the downloaded assets against `dist/`), then push `main`. Publishing before pushing `main` keeps Unraid's update check from finding a manifest whose files do not exist yet. On 2026-11-17 `git filter-repo --path dist --invert-paths` removed every package from history (a fresh clone went from 1.1 GB to 1.6 MB) and all branches and tags were force-pushed, so commit hashes from before then changed. GitHub's closed pull request refs (`refs/pull/*`) cannot be rewritten and still reference the old commits. Clones made before the rewrite need `git fetch --prune --force --tags` and `git reset --keep origin/main`; local branches based on the old history still carry the packages until deleted or rebased.
- On the Unraid host, launching `/usr/local/bin/kms_mosaic.bin` directly can miss packaged shared-library resolution. Use the `/usr/local/bin/kms_mosaic` wrapper or the userscript path, not the bare binary, when validating remotely.
- The package wrapper now exports `KMS_MOSAIC_REEXEC` so config-watch reloads come back up through `/usr/local/bin/kms_mosaic` instead of reexecing the bare binary. If plugin-managed startup loops and then dies on `libmpv.so.1`, check that the wrapper and packaged binary were rebuilt together.
- The native Unraid plugin now lives under `unraid-plugin/` and is built with `scripts/build_unraid_plugin.sh`. It depends on the Linux package already existing in `dist/`.
- A forced plugin reinstall can race a fresh artifact upload. If `/usr/local/sbin/plugin install ... forced` starts before the rebuilt `.txz` has finished copying into `/boot/config/plugins/kms.mosaic/`, the installer can fail with `xz: (stdin): Compressed data is corrupt`. Wait for `scp` or any other copy step to finish before forcing the reinstall.
- On Unraid, `/usr/local/sbin/plugin install /boot/config/plugins/kms.mosaic.plg forced` may still refuse to rerun a same-version plugin with `plugin: not re-installing same plugin`; for same-version local validation, copy completed artifacts first and apply the package/install steps directly or bump the manifest version.
- The KMS Mosaic package must not bundle or retain Unraid's Mesa/GLVND-facing graphics stack (`libEGL`, `libGL`, `libgbm`, `libdrm`, `libxcb`, `libX11*`, `libexpat`, `libz`, etc.). After an Unraid update, stale bundled transitive libraries can shadow the host GPU stack and make EGL fail with `eglGetDisplay: No such file or directory` even though the plugin boot hook ran.
- Do not purge every driver-adjacent mpv dependency from `/usr/local/lib/kms_mosaic`. This host does not provide libraries such as `libva*`, `libvdpau`, `libvulkan`, `libOpenCL`, `libmfx`, and `libsystemd`; removing the bundled copies makes `kms_mosaic.bin` fail to load before startup. Keep the cleanup focused on host Mesa/GLVND/DRM/X11-XCB stack libraries that Unraid must provide.
- Do not remove every `libX*.so*` from the package/runtime cleanup. mpv needs bundled libraries such as `libXss.so.1` on this host; the cleanup should target the host Mesa-facing X11/XCB libraries narrowly (`libX11*`, `libXau`, `libXdmcp`, `libXext`, `libxcb*`) rather than all X libraries.
- The plugin-owned web service must be started through `/usr/local/bin/kms_mosaic_web`, not by executing `kms_mosaic_web.py` directly, because the wrapper selects the Python venv that has `aiortc`/PyAV available.
- The Unraid plugin page no longer embeds the editor through an iframe. It now injects the editor directly into the plugin page, sources the HTML and config state from the packaged `kms_mosaic_web` wrapper, and only uses the web service for preview/media/WebRTC endpoints. If the plugin UI breaks while the standalone editor still works, check the wrapper-backed actions in `include/actions.php` and the HTML/JS rewrite path in `KMSMosaic.page` first.
- The plugin bootstrap does not call the standalone editor's normal initial `loadState()` path. `KMSMosaic.page` fetches `backend_state` itself and calls `fillForm(...)` directly, so any new startup behavior added only under `loadState()` must also be mirrored in the plugin wrapper or it will work standalone but silently fail on the embedded Unraid page.
- The current intended plugin route is the Settings-side `KMSMosaic` page, but the page itself must still behave like a full standalone plugin surface, not like two separate settings pages bolted together. Keep the service controls folded into the main page and preserve a normal plugin-launch experience from the Plugins tab.
- If the plugin web service looks alive in the browser but reports `web_running=false`, treat stale PID-file handling as a first suspect. The service script now falls back to `pgrep` on the `kms_mosaic_web.py --config ... --port ...` command line.
- The plugin install path now retires the old `Start kms_mosaic` userscript by renaming it to `Start kms_mosaic.disabled-by-kms-mosaic-plugin`. If boot ownership seems inconsistent after plugin install or removal, check both paths.
- If the Settings page keeps serving an older `KMSMosaic.page` after reinstall, check for duplicate copies anywhere under `/usr/local/emhttp/plugins` first. Older bad bundles left nested trees like `/usr/local/emhttp/plugins/usr/local/emhttp/plugins/kms.mosaic/KMSMosaic.page`, and even manual backups such as `/usr/local/emhttp/plugins/kms.mosaic.backup/KMSMosaic.page` can override the real page. Move stale copies fully out of `/usr/local/emhttp/plugins`; renaming them in place is not enough.
- The Installed Plugins page does not render the `.plg` `description` attribute for installed plugins. It renders `README.md` from `/usr/local/emhttp/plugins/<plugin>/README.md`, with the plugin name as a fallback if that file is missing. If the Plugins page shows `kms.mosaic` with no summary, package a `README.md` into `unraid-plugin/package-root/usr/local/emhttp/plugins/kms.mosaic/`.
- Unraid Settings-side `.page` files need the metadata preamble at the very top, for example `Menu="Utilities"`, `Title="..."`, `Icon="..."`, then `---`, before any PHP or HTML. If that header is missing, the plugin can disappear from the Settings tiles and `/Settings/<PageName>` can render as an empty shell even though the `.page` file exists.
- Installing a second manifest file name such as `kms.mosaic.local.plg` creates a second Installed Plugins entry even if the inner `<PLUGIN name="kms.mosaic">` is identical. Avoid leaving extra top-level `.plg` files under `/boot/config/plugins/`; keep only `/boot/config/plugins/kms.mosaic.plg` for this plugin.
- The repository architecture described in older docs may be stale. The current compositor is already split across `app`, `display`, `media`, `render_gl`, `frame`, `panes`, `layout`, `options`, `runtime`, and `ui` modules.
- The compositor’s live runtime, option parsing, and layout output now allocate pane/role storage dynamically from `pane_count`. The main remaining legacy assumptions are mostly user-facing naming/help shortcuts (`--pane-a` through `--pane-d`) and related labels, not fixed-cap live buffers.
- The companion web UI is now a tree-first editor rather than just a static form. It saves `--split-tree` specs, demotes legacy scene/raw config fields into Advanced sections, and uses a WebRTC preview path instead of the older browser-side BMP/snapshot loop.
- The pane inspector now has structured per-pane mpv controls layered on top of pane-local raw mpv options. If you add another pane-local mpv setting, update both the structured parser/builder in `tools/kms_mosaic_web.py` and the raw fallback textarea handling so they stay in sync.
- The web API's `/api/state` response is now shaped as `{ config_path, raw_config, state }`. If you smoke-check it manually, don't expect pane/layout fields at the top level.
- Compositor preview files are still written via temp-file rename before the WebRTC bridge consumes them. If the live preview starts showing torn frames again, treat that as a compositor-side regression first, not just a browser/UI bug.
- `tools/kms_mosaic_web.py` may have live user edits that have not been committed yet. Check the local diff before changing it and patch surgically instead of assuming the repo version is authoritative.
- `tools/kms_mosaic_web.py` currently defines `write_text_atomic()` twice; the later definition overrides the earlier one. Keep their behavior aligned until they are deliberately consolidated.
- The current Unraid web-preview venv has AV1 encoders available through PyAV, but `aiortc` still only advertises `VP8`, `H264`, and the locally patched `VP9` codec layer. Better CPU headroom does not make AV1 available by itself; adding AV1 requires codec-layer support in `aiortc`, not just encoder presence in FFmpeg/PyAV.
- A failed or partial plugin install can leave a zero-byte cached plugin bundle under `/boot/config/plugins/kms.mosaic/`. If the Unraid plugin extractor starts failing unexpectedly, verify the cached `.tgz` on the host before blaming the install script.
- The remaining explicit user follow-ups are now narrower: improve the preview toward a truer 1:1 mirror, add direct drag/resize handles in the Layout Studio, and expose more common mpv options as structured controls so fewer edits need the raw advanced text.
- The plugin-hosted settings page must not reuse DOM ids from the embedded editor. Reusing ids like saveBtn/reloadBtn makes the embedded JS bind to the wrong controls and silently breaks config save/reload from the page.
- If playback starts stuttering intermittently after reloads, inspect the live process tree for orphaned pane children first. Older builds could leave `btop`, `tail`, or other pane commands running under `init`, which adds random extra load even though the current pane tree looks normal.
- Multi-mpv-pane playback needs `mpv_render_context_report_swap()` called for every pane-local mpv context after present, not just the primary video context. If pane-local video gets strangely choppy while CPU looks fine, inspect `src/frame.c` before blaming decode settings.
- Multi-pane mpv rendering should not share one scratch video FBO across differently sized panes. That can trigger repeated texture/FBO reallocations, intermittent GPU stalls, and big RSS swings even when the config is unchanged.
- Embedded libmpv playback should default to `load-scripts=no` unless the user explicitly overrides it. On this Unraid host, leaving mpv's built-in scripts enabled caused large intermittent `START_FILE -> FILE_LOADED` stalls in both the main queue and pane-local queues even when shaders, storage, and hardware decode were otherwise healthy.
- If a pane disables audio with `audio=no`, also force `aid=no` unless the user explicitly set `aid`. On this host, some H.264+Aac clips still incurred multi-second `START_FILE -> FILE_LOADED` stalls until audio track selection was disabled as well.
- Until 2026.11.17.3 the package bundled Ubuntu 22.04's libva 2.14, which cannot load TOWER's Mesa VA driver (`radeonsi_drv_video.so` from Mesa 26.2.5 exports only `__vaDriverInit_1_24`, and libva looked in `/usr/lib/x86_64-linux-gnu/dri`, which Unraid does not have). VA-API never worked, `auto-copy-safe` fell back to CPU decoding, and the old `hwdec=vaapi` queue stalls were probably that failure repeating per file. Once the RTX 3090 Ti was bound to the `nvidia` driver on 2026-11-17, `auto-copy-safe` picked NVDEC on it instead. The build now compiles libva 2.24.1 (pinned by SHA-256) and bundles it. If Unraid's Mesa moves past VA-API 1.24, libva logs `has no function __vaDriverInit_1_N` and decoding silently returns to the CPU; the amdgpu `drm-engine-dec` counter in `/proc/<pid>/fdinfo` shows whether hardware decode is running.
- Since 2026.11.17.6 the package is built on Debian trixie (libmpv 0.40, FFmpeg 7.1, glibc 2.41; TOWER has glibc 2.44) instead of Ubuntu 22.04 (libmpv 0.34). Embedded mpv decodes zero-copy (`hwdec=vaapi`, `gpu-hwdec-interop=vaapi`) on the render node of the DRM card being displayed: `app.c` fills a `media_decode_device` (path from `drmGetRenderDeviceNameFromFd()`, plus an open fd) and every mpv render context gets the fd as `MPV_RENDER_PARAM_DRM_DISPLAY_V2` `render_fd`; `vaapi-device` gets the path for an explicit `vaapi-copy`. `Video decode device:` in `/tmp/start_kms_mosaic.log` names it. libmpv 0.34 ignored dmabuf format modifiers when importing VA surfaces, so zero-copy drew horizontal green bands across every video with Mesa 26.2.5; 0.40 passes them and the picture is clean. In mpv 0.34 the interop was named `vaapi-egl`; in 0.40 it is `vaapi`, and an unknown name loads no interop and silently decodes on the CPU. Restricting `gpu-hwdec-interop` matters: libmpv otherwise loads every interop when the render context is created, and the `cuda-nvdec` probe initializes CUDA on any NVIDIA card (6 handles on `/dev/nvidia*`, `libcuda` mapped) even though the display is AMD. The EGL display comes from `eglGetPlatformDisplay(EGL_PLATFORM_GBM_KHR, ...)`; the legacy `eglGetDisplay` makes GLVND ask NVIDIA's EGL vendor to guess the platform, which opens 5 more NVIDIA handles. On TOWER (2026-11-17, same build, preview closed, interleaved 60 s windows) zero-copy used 65-71% of one core against 79% for `vaapi-copy`: mpv's threads fell from 62% to 12%, but the main thread rose from 16% to 53-58%, partly importing each frame (`dri2_from_dma_bufs`). With this build, config reloads out of a `vaapi-copy` process wedged 2 of 3 times (no `config-reload` event, then `render-timeout` and a watchdog restart about 25 s later), while 9 of 9 reloads out of zero-copy were clean. To check a decode change visually without the monitor, touch `/tmp/kms_mosaic_snapshot.request` and read `/tmp/kms_mosaic_preview.rgba` (8-byte little-endian width and height, then RGBA rows).
- On this Unraid host, stopping `kms_mosaic` can leave both HDMI connectors disabled even after the original CRTC is restored. If the monitors stay black after stop, rebind the framebuffer console under `/sys/class/vtconsole/*/bind`, unblank `/sys/class/graphics/fb*/blank`, and force `tty1` back to `KD_TEXT`; the compositor cleanup path needs the fbcon restore step, not just `drmModeSetCrtc()`.
- Synchronous `mpv_get_property*()` calls from `media_handle_wakeup()` are not safe on this host. During a black-screen/blank-preview failure, the main thread wedged inside `mpv_get_property_string("path")` from the wakeup callback path before frame 0 completed. If preview/output goes black while the process stays alive, inspect `src/media.c` first and avoid blocking property reads from the mpv wakeup handler.
- On this Unraid host, forcing embedded libmpv to `keep-open=yes` is also a known bad path for queued pane playback. It can turn clip changes into multi-second apparent freezes even when `END_FILE -> START_FILE` is immediate; default pane playback should keep `keep-open=no` unless the user explicitly overrides it.
- On this Unraid host, the six-pass Anime4K `glsl-shaders=` stack on pane-local mpv contexts can dominate next-file handoff time by itself. In live captures, the same pane queues dropped from roughly `5-19s` `START_FILE -> FILE_LOADED` stalls to sub-second when those pane shader lines were removed. Enabling `gpu-shader-cache=yes` by default helped some entries but did not eliminate the worst-case pauses with the full stack still present, so treat heavy custom shader stacks as the first suspect if queue handoffs are still freezing after the other mpv defaults have been cleaned up.
- `src/media.c`'s async `loadfile` path for queued items with per-file mpv options builds temporary `mpv_node` trees that libmpv does not own. If that path stops freeing the command tree after `mpv_command_node_async()`, long queue runs can ratchet compositor RSS upward even when the web plugin is stable.
- If the array is intentionally stopped during boot, such as during disk replacement, plugin startup must not synchronously wait on `/mnt/...` media paths. The service script should detect a stopped Unraid array, skip compositor startup quickly, let the web service and boot continue, and rely on the array `started` event to launch the compositor later.
- TOWER's aiortc 1.14 H.264 sender starts at 1 Mbps and caps at 3 Mbps, does not expose `RTCRtpSender.getParameters()`/`setParameters()`, and does not raise its encoder limit from `x-google-*` SDP hints. Preview profiles must configure the aiortc H.264 module's actual `DEFAULT_BITRATE`, `MIN_BITRATE`, and `MAX_BITRATE` before negotiation if higher bitrate is required.
- Bitmap terminal fonts such as the bundled Tiny5 Mono (`--font /usr/local/share/kms_mosaic/fonts/Tiny5Mono.bdf`) render only at whole multiples of their 6x9 cell. `panes_fit_font_px()` still enforces each pane's minimum columns and rows, so a narrow pane that cannot fit at 2x drops to 1x (6x9) instead of an in-between size. The second pane's minimum is 45x16 so TOWER's 540x345 px syslog pane fits at 2x (45x19 cells). TOWER's fontconfig `monospace` has no Braille glyphs, so btop graphs show empty boxes with the system font.
